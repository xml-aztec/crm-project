# design-sync notes — CRM UI Kit

## Repo shape

This is NOT a standalone design-system package — it's `src/components/ui/` and
`src/components/form/` inside the `tailadmin-react` CRM app (see
`/Users/nurlan/Documents/GitHub/crm-project/CLAUDE.md`). There is no library
build, no `.d.ts` output, no Storybook. Per user decision, only the reusable
primitives are synced — domain-specific components (orders/, payroll/,
customers/, etc.) and page-level demo compositions are out of scope.

## Why a curated entry instead of synth-entry

The converter's synth-entry fallback (no `dist/`, no `cfg.entry`) walks the
WHOLE `srcDir` and does `export * from <every .tsx/.jsx file>` — that would
have bundled the entire CRM app (pages, Redux, RTK Query hooks, routing) into
the DS bundle. Instead, `.design-sync/entry/index.tsx` is a hand-maintained
curated entry that re-exports exactly the scoped primitives. **Add a line
there (and a `componentSrcMap` entry) when a new primitive enters scope.**

## Why cssEntry points at a vite build output, not src/index.css

`src/index.css` only defines Tailwind v4 `@theme` tokens and custom
`@utility` rules — the actual utility classes components use (`rounded-lg`,
`bg-brand-500`, etc.) are generated by Tailwind's content scan at build time
and don't exist statically in that file. `cfg.cssEntry` therefore points at
`.design-sync/build/app.css`, a copy of the real Vite build output
(`dist/assets/index-*.css`), which contains every generated utility class
the whole app uses (safely over-inclusive). **Regenerate before every
build/resync** — `cfg.buildCmd` is the exact recipe:
```
npx vite build && cp dist/assets/index-*.css .design-sync/build/app.css
```
(`vite build` alone, not `npm run build` — the latter also runs `tsc -b`,
which is slow and irrelevant here: we only need the compiled CSS, not a
type-check of the whole app.)

## Explicitly excluded (dead code / not real primitives)

Deliberately left out of `componentSrcMap` — re-add only if the user asks:
- `src/components/ui/Toggle.tsx`, `src/components/ui/DatePicker.tsx`,
  `src/components/ui/DatePickerVariants.tsx`, `src/components/form/date-picker.tsx`
  — unused TailAdmin template leftovers (verified via grep: zero imports
  anywhere in `src/`). The actually-used date picker family is
  `src/components/form/DatePickerVariants.tsx` (imported by
  `OrdersFilters.tsx`, `SuppliesManagement.tsx`, `StockLogsPage.tsx`) — that's
  the one in scope.
- `src/components/ui/images/*`, `src/components/ui/videos/*` — zero-prop
  hardcoded demo sections, only used by `pages/UiElements/Images.tsx` and
  `Videos.tsx` (TailAdmin's own showcase pages, not real CRM features).
- `src/components/form/form-elements/*` (DefaultInputs, FileInputExample,
  CheckboxComponents, ToggleSwitch, etc.) — page-level demo compositions, not
  reusable primitives (user's explicit scope decision).

## Grouping

The folder-heuristic group derivation collapses to `general` for almost
everything here (e.g. `ui/button/Button.tsx` → parent dir `button` matches
the component's own name, grandparent `ui` is in the generic-dir list — both
get filtered, nothing left to group by). Fixed via `cfg.docsMap` stub files
under `.design-sync/groups/*.md` (frontmatter-only, `category: <Group>`) —
Actions, Feedback, Overlays, Data Display, Forms.

## Naming

- `Input` (not `InputField`) — matches how it's imported everywhere in the
  app (`import Input from '.../input/InputField'`).
- `FormDatePicker`/`DateTimePicker`/`DateRangePicker`/`FilterDatePicker`/
  `FutureDatePicker`/`PastDatePicker` all come from one file,
  `form/DatePickerVariants.tsx`.

## Scope decisions (from the user, 2026-06-19)

- Primitives only, not the full `ui/`+`form/` tree (excludes demo files above).
- Preview depth: **floor cards for now** — every component ships fully
  functional and importable, but no hand-authored rich previews yet. They can
  be authored incrementally on a later re-sync (this is the documented
  "floor card" behavior, not a failure state).

## Known render warns

- `DropdownItem` `tag="a"` variant (renders via react-router's `Link`) can't
  be previewed: wrapping it in a separately-imported `MemoryRouter` in the
  preview file gets bundled as a distinct react-router instance from the one
  `DropdownItem.tsx` itself uses, so `Link`'s `useContext` comes back `null`
  ("Cannot destructure property 'basename'..."). Dropped that preview
  variant; only the `tag="button"` usage (the common case) is previewed.

## Re-sync risks

- `componentSrcMap` and the curated entry file are hand-maintained — a new
  primitive added to `ui/`/`form/` won't appear in the DS project until both
  are updated.
- `cssEntry` is a snapshot of a full app build; if Tailwind classes used only
  by non-scoped components get purged/added differently in a future
  refactor, re-run `cfg.buildCmd` before re-syncing rather than trusting a
  stale `.design-sync/build/app.css`.
- No render-check has been run yet as of this writing (see config.json
  timestamp / git history for when this note was last true).
