# Чего не хватает и что делать дальше

## Чего не хватает

Система (см. [features.md](./features.md)) по факту — скорее **ERP** для управления товарным бизнесом (каталог → склад → заказы → поставки → финансы → зарплата), чем классическая **CRM** в узком смысле. Из типичного набора CRM/ERP функций для розничной/оптовой торговли в коде подтверждённо отсутствуют:

- **Воронка продаж / сделки**. Нет сущности «лид» или «сделка» со стадиями (новый → в работе → выигран/проигран) — процесс начинается сразу с клиента и заказа. Если бизнесу нужно вести работу с потенциальными клиентами до момента заказа (звонки, встречи, коммерческие предложения) — этого функционала нет вообще.
- **Задачи и напоминания**. Есть только просмотровый календарь (без создания/редактирования событий) и системные уведомления (заказ создан/пользователь одобрен). Нет модуля «поставить задачу сотруднику», «напомнить о звонке клиенту» и т.п.
- **Настраиваемые уведомления**. Раздел в настройках — открытая заглушка с планом на будущее (без единой рабочей функции сверх email при регистрации/одобрении/сбросе пароля и internal-колокольчика).
- **Экспорт данных за пределами каталога**. Экспортировать можно только товары (CSV/Excel). Клиентов, заказы, финансовые отчёты (P&L, кассовые потоки) можно только просматривать в интерфейсе — выгрузить в файл нельзя.
- **Возвраты/RMA**. Есть отмена заказа (полностью, с возвратом остатка), но нет отдельного механизма частичного возврата товара после подтверждения заказа.
- **Расширенный аудит**. Полноценная история изменений (кто/когда/что) есть только для заказов (`order_history`). Изменения цены товара, прав доступа, финансовых записей и т.п. нигде не логируются отдельно.
- **Мультивалютность**. Форматирование цены (`Intl.NumberFormat(..., currency: 'KGS')`) жёстко зашито на сомы — если потребуется работа в нескольких валютах (например, закупка у зарубежных поставщиков), этого сейчас нет.
- **Глобальный поиск**. У каждого раздела свой фильтр/поиск, но нет единой строки поиска «по всей системе» (клиент, заказ, товар одновременно).
- **Интеграции**. Нет интеграций с платёжными шлюзами, бухгалтерскими системами, мессенджерами — ни в зависимостях, ни в конфигурации это не просматривается.

## Достаточно ли текущего функционала для полноценной эксплуатации?

**Частично.** По объёму бизнес-логики — это не прототип: складской учёт с резервированием и проверкой на списание в минус, аудит заказов, ABC/XYZ-анализ, P&L, зарплата с KPI, RBAC с кастомными ролями, генерация PDF-накладных и QR/штрихкод-сканирование — всё это реально работает, не заглушки. Для повседневного оформления заказов, учёта остатков и базовой отчётности систему уже можно использовать.

Но есть три конкретные причины **не** запускать её на реальных деньгах и данных без доработки прямо сейчас:

1. **Два подтверждённых сценария безвозвратной потери данных** при рутинных админ-действиях — удаление клиента стирает всю его историю заказов, удаление филиала может стереть остатки/склад/историю поставок целого филиала (см. [known-issues.md](./known-issues.md#критично-целостность-данных)). Оба возможны одним кликом, без предупреждения, без бэкапа «из коробки».
2. **Ноль автотестов** на самой рискованной логике — заказы (списание/возврат склада), перевод остатков, зарплата, вся финансовая аналитика. Любое дальнейшее изменение кода в этих модулях ничем не подстраховано.
3. **Деплой-конфигурация внутренне противоречива** (см. известные проблемы, п. 7) — при попытке развернуть систему «как есть» велик шанс использовать нерабочий/устаревший конфиг.

Вывод: технически система близка к продакшен-уровню по глубине функциональности, но нуждается в исправлении конкретных, уже найденных рисков прежде, чем доверить ей реальные операционные данные.

## Приоритизированный план

### Критично (блокирует безопасную эксплуатацию)

1. **Убрать каскадное удаление Customer→Orders и Branch→Warehouses** (или добавить защиту/предупреждение по аналогии с уже существующей проверкой в `categories.py::bulk_delete`). *Почему*: единственный найденный сценарий тихой безвозвратной потери финансовых/складских данных обычным пользовательским действием.
2. **Покрыть тестами заказы (подтверждение/отмена/списание-возврат склада) и зарплату (генерация/пересчёт)**. *Почему*: это код, который двигает деньги и остатки товара — сейчас изменить его без риска регрессии невозможно.
3. **Добавить проверку владения в `/orders/{id}/items/*`, `/orders/{id}/confirm`, `/orders/{id}/status`** (переиспользовать существующий `is_order_owner_or_admin`). *Почему*: сейчас один менеджер технически может изменить/подтвердить чужой заказ, зная его ID.
4. **Вернуть автоопределение `BASE_URL`/`FRONTEND_URL` на Render** (функция `_default_urls_from_render` была удалена коммитом `295663b`, хотя `render.yaml` на неё рассчитывает) — либо явно задать обе переменные в конфигурации Render до первого деплоя. Заодно вычистить мёртвые следы Fly.io/Railway ([known-issues.md, п. 8](./known-issues.md#8-мёртвая-конфигурация-flyio-и-railway-целевой-хостинг--rendercom)). *Почему*: без этого прод-деплой на подтверждённый хостинг (Render.com) отправит JWT-куки с `secure=False` — прямая регрессия уже закрытой ранее уязвимости — и сломает ссылки сброса пароля.

### Желательно (существенно повышает ценность продукта)

5. **Довести RBAC до записи** — подключить `require_permission` к create/update/delete, а не только к чтению шести ресурсов. *Почему*: UI управления ролями уже обещает такую гранулярность, бэкенд её не выполняет.
6. **Унифицировать проверку «админ ли пользователь» на фронтенде** — перевести `useRoleAccess` на реальные RBAC-права вместо легаси `role.name`. *Почему*: бэкенд уже полностью на RBAC (Stage D), фронтенд частично отстал — риск рассинхронизации UI и реальных прав.
7. **Экспорт данных за пределы каталога** — хотя бы клиенты, заказы, P&L/кассовые потоки в Excel/PDF. *Почему*: это стандартная потребность бизнеса (бухгалтерия, резервные копии, анализ вне системы), сейчас доступна только для товаров.
8. **Оформить и задокументировать стратегию бэкапов БД**, независимо от выбранного хостинга. *Почему*: при наличии финансовых и складских данных, а также при известных рисках каскадного удаления (см. п. 1), рабочий бэкап — не опция, а необходимость.
9. **Исправить N+1-запрос в листинге товаров** (`repositories/product.py::get_filtered`). *Почему*: сейчас не критично, но деградирует линейно с ростом каталога — дешевле исправить сейчас, чем при реальном объёме данных.
10. **Решить судьбу раздела «Уведомления»** — либо реализовать (хотя бы email-предпочтения), либо убрать «в разработке» из UI, если не в приоритете. *Почему*: витрина без функции создаёт ложные ожидания у пользователей системы.

### Опционально (не блокирует, можно откладывать)

11. Достроить календарь до полноценного модуля задач/напоминаний (CRUD события, привязка к заказам/клиентам) — или явно исключить его из релиза, раз он сейчас лишь витрина поверх FullCalendar.
12. Расширить аудит изменений за пределы заказов (цены товаров, права доступа) — если для бизнеса важна прослеживаемость таких изменений.
13. Мультивалютность — только если бизнесу реально нужно работать не только в сомах.
14. Глобальный поиск по системе.
15. Убрать мёртвый код и зависимости из [known-issues.md](./known-issues.md) (`Supplies.tsx`-заглушка, `weasyprint`, `aiosqlite`, устаревшие докстринги про «Stage C») — низкий риск, но чистит кодовую базу для новых разработчиков.
16. Убрать неиспользуемые демо-страницы шаблона TailAdmin (`FormElements`, `BasicTables`, `Charts/*`, `UiElements/*`, `Blank`), если они не нужны — сокращает поверхность продукта и путаницу при онбординге.
