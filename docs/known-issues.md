# Известные проблемы и технический долг

Все пункты ниже проверены построчным чтением кода и/или прямым запуском инструментов (`npm audit`, `pip-audit`) на 29.08.2026 — не переписаны из старых отчётов без проверки. Где отмечено «предположение» — это неподтверждённая гипотеза, требующая уточнения у команды.

## Критично: целостность данных

### 1. Удаление клиента безвозвратно удаляет его заказы
`app/models/customer.py`: `orders = relationship("Order", back_populates="customer", cascade="all, delete-orphan")`. При этом `orders.customer_id` объявлен как `ForeignKey(..., ondelete="SET NULL")` — то есть по замыслу проекта заказ должен **пережить** удаление клиента (принцип явно описан и правильно реализован для Brand/Subcategory → Product). Но ORM-уровневый `cascade="all, delete-orphan"` заставляет SQLAlchemy удалить все заказы клиента *до* того, как сработал бы DB-уровневый `SET NULL`. Через дальнейший каскад (`Order.items` тоже `delete-orphan`, `order_items.order_id`/`order_history.order_id` — `CASCADE` в БД) вместе с заказом исчезают все его позиции и вся история изменений.

`DELETE /customers/{id}` (`repositories/customer.py::delete`) не делает никакой проверки на существование заказов и не предлагает `force`-подтверждение (в отличие от `bulk_delete` категорий, где такая защита есть).

**Как исправить**: убрать `cascade="all, delete-orphan"` с `Customer.orders` (оставить обычную `relationship` без каскада, как у Brand/Subcategory), либо явно заблокировать удаление клиента с активными заказами по аналогии с `categories.py::bulk_delete`.

### 2. Удаление филиала может стереть весь склад и историю поставок
`app/models/branch.py`: `warehouses = relationship("Warehouse", back_populates="branch", cascade="all, delete-orphan")`, при этом `warehouses.branch_id` — `ondelete="SET NULL"`. Та же природа проблемы, что и с клиентом, но с более тяжёлыми последствиями: удаление склада (через каскад от филиала) на уровне **БД** тянет за собой `ondelete="CASCADE"` по `product_stock.warehouse_id`, `stock_logs.warehouse_id` и `supplies.warehouse_id` (а через `Supply.items` — ещё и все `supply_items`).

Итог: один клик «удалить филиал» способен без предупреждения уничтожить текущие остатки, весь журнал движений товара и всю историю поставок для всех складов этого филиала. `repositories/branch.py::delete` и `repositories/warehouse.py::delete` не делают вообще никаких проверок.

**Как исправить**: то же, что и выше — убрать каскадное удаление либо добавить проверку/подтверждение перед удалением непустого филиала/склада.

### 3. Удаление сотрудника стирает его зарплатную историю и KPI-планы
`payrolls.user_id` и `monthly_targets.manager_id` — оба `ondelete="CASCADE"` на уровне БД (согласовано с ORM-каскадом на `User`, в отличие от п. 1–2). Формально не баг рассинхронизации, но с точки зрения бизнеса — вероятно, нежелательное поведение: удаление учётной записи уволенного сотрудника уничтожает историю его зарплат и планов, хотя в модели уже есть поле `is_active`, пригодное для «мягкого» увольнения без потери истории. `DELETE /users/{id}` не предупреждает об этом эффекте.

## Высокий приоритет: безопасность / авторизация

### 4. Управление позициями заказа не проверяет владение заказом
`POST/PATCH/DELETE /orders/{order_id}/items/...` (`api/order_items.py`) требуют только `Depends(get_current_user)` — **любой** авторизованный пользователь (в том числе менеджер без доступа к этому конкретному заказу) может добавить, изменить или удалить позицию в **любом чужом заказе** по его ID. Для сравнения, `PATCH /orders/{id}` и отмена статуса заказа отдельно проверяют владельца/админа (`is_order_owner_or_admin` либо явная проверка в репозитории). `PATCH /orders/{id}/confirm` и `PATCH /orders/{id}/status` также используют только базовую авторизацию без проверки владения — то есть один менеджер потенциально может подтвердить/сменить статус чужого заказа, зная его ID.

**Как исправить**: применить `is_order_owner_or_admin` (уже существует в `core/dependencies.py` и используется для `PATCH /orders/{id}`) единообразно ко всем операциям изменения состояния заказа и его позиций.

### 5. Складские write-операции доступны любому авторизованному пользователю
`POST /stock/` (создание остатка), `PATCH /stock/{id}` (изменение количества), `POST /stock/transfer` (перевод между складами) и `DELETE /stock/{id}` в `api/product_stocks.py` требуют только `Depends(get_current_user)` — ни `is_admin`, ни `require_permission("stock.write"/"stock.update")` (при том что `stock.read` уже подключён к чтению этих же данных). Любой авторизованный сотрудник, включая только что одобренного менеджера, может напрямую менять остатки на любом складе или переносить товар между складами без какого-либо ролевого ограничения.

**Как исправить**: определиться, требуется ли здесь ограничение по роли/праву (если нет — явно задокументировать это как намеренное решение, а не пробел).

### 6. Фронтенд проверяет «админ ли пользователь» не через RBAC
`frontend/src/hooks/useRoleAccess.ts` вычисляет `isAdmin`/`isManager`/`canEdit`/`canDelete` локально из `user.role.name`/`user.role_id`, полностью в обход RBAC. При этом бэкенд (`app/rbac/service.py::user_is_admin`, комментарий "Stage D: RBAC is now the sole source of truth for admin access. The legacy `roles.name` fallback was removed…") **уже не использует** `roles.name` как источник истины для админ-доступа. Если администратор выдаст пользователю административные права через кастомную RBAC-роль без изменения его базовой роли (или наоборот — реальные права уже не совпадают с легаси-ролью), фронтенд будет показывать/скрывать разделы UI (`SettingsHub`, вкладки конфигурации и т.п.) не в соответствии с тем, что реально разрешит бэкенд. Не является уязвимостью (бэкенд — источник истины по факту запроса), но создаёт запутанный UX и риск «пользователь не видит кнопку, которая на самом деле должна быть доступна» или наоборот.

**Как исправить**: перевести `useRoleAccess` на данные из `usePermissions`/`GET /users/me/permissions`, либо полностью унифицировать оба хука.

### 7. RBAC гранулярно применён только к чтению
Во всём бэкенде `require_permission(...)` вызывается только с шестью кодами — все действия `.read`: `products.read`, `customers.read`, `orders.read`, `stock.read`, `supplies.read`, `cashflow.read`. Ни один код на `create`/`update`/`delete`/`approve`/`export`/`manage_roles`/`invite` (все они уже описаны в справочнике прав и доступны для выбора в UI `/settings/roles`) не подключён ни к одному эндпоинту — операции записи везде проверяются через грубый `is_admin`. Кастомная роль, созданная в UI с правом «Товары → Изменение» без «Управление ролями», на бэкенде физически не даст возможности редактировать товары, если у роли нет полного `is_admin`-статуса. Это ограничивает практическую пользу UI управления ролями — он позволяет настроить видимость, но не полноценные права записи.

## Средний приоритет: конфигурация и деплой

### 8. Мёртвая конфигурация Fly.io и Railway — целевой хостинг: Render.com
Целевой хостинг подтверждён командой — **Render.com**. В коде при этом остаются следы ещё двух хостингов, которые стоит вычистить:
- `nginx/default.conf` (не `.template`) хардкодит `proxy_pass https://leadflow-backend.fly.dev/` — Fly.io, по коммитам явно выведенный из эксплуатации. Этот файл **не используется** текущей Docker-сборкой (Dockerfile копирует `default.conf.template`, не `default.conf`) — мёртвый, вводящий в заблуждение файл, безопасно удалить.
- Комментарии в `Dockerfile`, `docker-entrypoint.sh`, `nginx/default.conf.template`, `core/config.py` явно говорят про **Railway** (динамический `$PORT`, разбор `postgres://`-строки «managed Postgres providers (e.g. Railway)») — сами механизмы рабочие и нужны (Render тоже прокидывает `$PORT` динамически), но комментарии стоит переписать под Render, чтобы не вводить в заблуждение.
- `Dockerfile-backend`/`Dockerfile-frontend` — отдельные образы для сценария «два сервиса», актуального для прежней схемы на Fly.io. `render.yaml` их не использует (использует корневой `Dockerfile`) — безопасно удалить или явно пометить устаревшими.

**Реальный, гораздо более важный баг, обнаруженный именно из-за проверки под Render** — см. пункт 8а ниже.

### 8а. `render.yaml` рассчитывает на функцию, которая была удалена
`render.yaml` полагается на то, что `BASE_URL`/`FRONTEND_URL` определятся автоматически через `_default_urls_from_render()` в `core/config.py` (комментарий в `render.yaml` прямо её называет). Эта функция была написана вместе с `render.yaml` (коммит `4dbc87e`), но **удалена** позже коммитом `295663b` ("refactor: remove unused imports and model_validator from config.py") — вероятно, по ошибке, как «неиспользуемый» код, хотя `render.yaml` на неё ссылался. Сейчас `RENDER_EXTERNAL_URL` нигде в кодовой базе не читается.

**Практическое следствие при деплое на Render «как есть»**: `BASE_URL` и `FRONTEND_URL` останутся на дефолтах `http://localhost:8000`/`http://localhost:5173`, из-за чего:
1. JWT-кука уйдёт с `secure=False` вместо `True` — прямая регрессия ранее закрытой уязвимости (`is_https = BASE_URL.startswith("https://")`).
2. Ссылка в письме сброса пароля будет вести на `localhost:5173`.
3. Домен фронтенда не попадёт в CORS `allow_origins` (некритично при монолитном деплое через один домен, но важно, если фронт и бэк разнесены).

**Как исправить**: вернуть чтение `RENDER_EXTERNAL_URL` в `config.py`, либо явно задать `BASE_URL`/`FRONTEND_URL` как обычные переменные в `render.yaml`/Render Dashboard до первого деплоя.

### 9. `.gitignore` исключает папку `docs`
Строка `docs` в корневом `.gitignore` означает, что вся документация, создаваемая в рамках этой задачи, **не будет закоммичена** и не попадёт в историю git, если это не исправить отдельно. Файлы физически на диске и полноценны, но git их не видит.

## Средний приоритет: зависимости

### 10. Известные уязвимости в зависимостях (проверено `npm audit` / `pip-audit`)

**Frontend** (`npm audit --production`): **3 high-severity** уязвимости в прямых зависимостях —
- `axios` (используется отдельным клиентом авторизации `src/api/axios.ts`) — несколько DoS/prototype-pollution/SSRF-класса advisory, фикс есть (`npm audit fix`).
- `form-data` (транзитивная) — CRLF-инъекция через незаэкранированные поля формы.
- `react-router` — открытый редирект, отсутствие валидации протокола, DoS через неэффективный роутинг.

**Backend** (`pip-audit`, инструмент не входит в проект — установлен отдельно для проверки): **84 известных advisory в 20 пакетах**. Большинство — транзитивные и dev-зависимости (`pytest`, `black`, `pygments`, `pip` сам по себе), но есть и эксплуатационно значимые:
- `cryptography` (используется `python-jose` для подписи/проверки JWT) — 7 advisory.
- `starlette` (ядро FastAPI, обрабатывает каждый HTTP-запрос) — 7 advisory.
- `python-multipart` (разбор всех file-upload запросов — импорт CSV/Excel каталога) — 6 advisory.
- `pillow` (генерация QR-кодов) — больше десятка advisory.
- `pdfkit` — 1 advisory без опубликованной версии-фикса.

Большая часть версий зафиксирована в `pyproject.toml` через caret (`^`) от версий полугодовой давности — часть фиксов может требовать выхода за пределы текущего диапазона (например, обновления самого FastAPI, тянущего `starlette`). Точечная оценка эксплуатируемости каждой из 84 advisory не проводилась — это разумный следующий шаг перед продакшен-деплоем, а не результат этого аудита.

### 11. Неиспользуемые зависимости
- `weasyprint` (`pyproject.toml`) — не импортируется нигде в `app/`. Вся генерация PDF идёт через `pdfkit` (wkhtmltopdf), под который в `Dockerfile` специально ставится системный бинарник. `weasyprint` — мёртвый груз (увеличивает время установки/размер образа, и сам содержит открытые advisory — см. п. 10).
- `aiosqlite` — тесты (`backend/tests/conftest.py`) используют реальный `SessionLocal`/PostgreSQL, SQLite нигде не задействован.

### 12. Мёртвый и рассинхронизированный код
- `frontend/src/pages/supplies/Supplies.tsx` — целая нерабочая страница-заглушка, не импортируется и не роутится нигде (реальная страница — `SuppliesManagement.tsx`). Похоже на брошенный черновик.
- `backend/app/models/order_item.py` — закомментированный код (`# @property def product_name...`).
- `backend/app/core/logging_config.py`: `structlog.dev.ConsoleRenderer() if False else structlog.processors.JSONRenderer()` — мёртвая ветка тернарного оператора (видимо, временный переключатель для локальной отладки, оставленный в коде). Не баг, но стоит упростить до одной строки.
- `backend/app/rbac/dependencies.py` — докстринг модуля утверждает «Not wired into any router yet (Stage C)», хотя `require_permission` реально подключён к 9 роутерам. `backend/app/rbac/models.py`, докстринг `RbacRole` — упоминает «Stage C», тогда как `rbac/service.py` уже говорит про «Stage D». Комментарии не успевают за фактическим прогрессом миграции на RBAC — не блокирует работу, но сбивает с толку при чтении кода.
- Фронтенд держит два независимых HTTP-клиента для авторизации: `src/api/axios.ts` (axios, используется `store/slices/authSlice.ts`) и RTK Query `store/api/authApi.ts` — дублирование одной и той же логики (login/logout/getCurrentUser) двумя разными механизмами.

### 13. N+1-запрос в листинге товаров
`backend/app/repositories/product.py::get_filtered` после выборки списка товаров в цикле на Python выполняет отдельный `SELECT SUM(quantity) ...` **на каждый товар** для подсчёта `available_quantity`. При текущих объёмах данных не критично, но линейно деградирует с ростом каталога (список из 1000 отфильтрованных товаров = 1000 дополнительных запросов к БД). Стоит заменить на один агрегирующий JOIN/подзапрос.

## Тесты

### 14. Backend: тесты есть, но покрывают не самое рискованное
31 интеграционный тест (`backend/tests/`, httpx против реального приложения + реальный PostgreSQL) покрывают: health, auth (логин/логаут/неодобренный пользователь), RBAC (сидинг прав, миграция легаси-ролей, назначение ролей), password reset (весь цикл, включая истёкший/использованный токен), товары (базовый доступ), бренды/категории/подкатегории (пагинация, bulk-операции, защита от разрыва связей), импорт/экспорт Excel.

**Полностью без тестов**: заказы (включая списание/возврат склада — самую чувствительную к данным логику во всём проекте), перевод остатков между складами, поставки и поставщики, зарплата (генерация/пересчёт/выплата), вся аналитика (P&L, ABC/XYZ, KPI, лидерборд), кассовые потоки/бюджеты/прогноз разрывов, клиенты, уведомления, филиалы/склады, справочники (должности, способы оплаты, статусы заказов).

### 15. Frontend: тестов нет вообще
Ни `vitest`, ни `jest`, ни один файл `*.test.*`/`*.spec.*` в `frontend/`. Вся проверка сейчас — ручная и типами TypeScript.
